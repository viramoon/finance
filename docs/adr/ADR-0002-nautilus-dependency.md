# ADR-0002：Nautilus 依赖与替换策略

状态：已采纳（设计，尚未实现）

依据：issue #1 方案 v2 的方案 C

适用范围：finance

## 决策

把 NautilusTrader 作为依赖，不 fork、不修改其源码。改动前先查上游已有组件；需要新增能力优先用扩展点，或向上游提 PR。finance 不复制自研 core / connector / execution / backtest / py-bindings。

版本锁定方式 TBD：实施时选定具体发布版本、Rust / Python 兼容范围和依赖锁文件，记录升级验证结果；本次不创建依赖配置。

## LGPL-3.0

按本方案，作为依赖库自用且不分发时，没有新增的分发义务。将来若分发包含修改过 Nautilus 的程序，需要按 LGPL 提供修改部分源码并允许替换该库；分发方案变化时在对应 issue 核对履行方式。当前规则是禁止 fork 或改 Nautilus 源码，并保留依赖许可证与来源记录。

## 自研替换触发与流程

触发条件：可复现且经过测量的性能瓶颈、上游确实缺少的必要能力、无法接受的兼容或维护风险。先评估配置、扩展点及上游修复，不能仅因个人偏好替换。

提出独立 issue 和新 ADR，记录缺口证据、替代边界、兼容接口、数据迁移、验证、回退和维护成本；用相同数据与故障场景对比，经评审后逐项替换，不能在无关任务顺手重构核心。
